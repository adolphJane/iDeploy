# iDeploy 服务端 Agent 实施规划

## 目标与边界

iDeploy 首次保存并成功验证服务器连接后，通过 SSH 安装与桌面应用同版本的 Linux Agent。后续服务器操作优先调用 Agent 的结构化 API；SSH 保留为首次引导、修复和升级通道。`TestServerConnection` 仍只测试连接，不安装软件。

桌面端继续负责用户意图、持久化 Job Runner、部署历史、确认流程和 Keychain 凭据。Agent 负责本机状态观察、受限操作、操作日志与远端幂等记录。Agent 不直接读取桌面端 SQLite，也不接受任意 Shell 命令。首版只支持 Linux amd64/arm64 与 systemd；其他系统维持 SSH 模式并显示原因。

## 首次连接与生命周期

1. 用户保存服务器后创建 `server.agent.bootstrap` Job。先走现有 SSH 主机指纹和身份验证，再查询 OS/架构、systemd、Docker 和可写安装目录。
2. 从应用包选取对应 Agent 二进制，验证本地发布清单中的 SHA-256；经 SSH 标准输入上传至服务器临时文件，远端再次校验哈希。不得下载未经验证的远端脚本执行。
3. 将版本文件原子移动到 Agent 专用目录，保存上一版本，安装 systemd unit，启动服务。安装文件权限和目录权限固定；先健康检查再切换当前版本。
4. Agent 仅监听服务器 `127.0.0.1`；桌面端建立 SSH 端口转发并完成版本、身份和能力握手，不额外开放公网端口。每台服务器使用独立的配对凭据，桌面端存 Keychain，服务器端文件设为仅 Agent 可读；API 请求经认证并设超时、大小限制和重放保护。
5. 首次清单同步后，服务器详情显示 Agent 版本、连接状态、能力、上次心跳与更新结果。安装失败不删除服务器记录，Job 记录具体阶段并提供重试。
6. 升级采用“上传新版本 → 校验 → 切换 → 健康检查”的流程；失败自动恢复上一版本。卸载 Agent 必须是独立显式操作，不随“移除服务器”默认删除远端文件。

首版不要求桌面应用持续在线。断线后 Agent 继续完成已接受的远端操作；桌面端重连时按 operation ID 对账，不把网络超时误判为操作失败。

## 通信与操作协议

在现有 `internal/server` 上方增加 `RemoteExecutor` 边界：`SSHExecutor` 保留现有实现，`AgentExecutor` 逐项接管。调用方选择具备所需 capability 的执行器；对于已经被 Agent 接受的写操作，断线后只能查询同一个 operation ID，不自动退回 SSH 重做。

首版 API 采用版本化的本地 HTTP/JSON 或 gRPC 协议，经 SSH 隧道承载；协议选择在实现前固定，避免两套客户端。至少包含：

| 接口 | 内容 |
| --- | --- |
| `hello` / `capabilities` | Agent/API 版本、OS/架构、Docker/Nginx/Certbot 能力、健康状态 |
| `inventory` | 容器、端口、Compose 项目、现有 Nginx 路由和证书的只读快照 |
| `system.metrics` | CPU、内存、交换空间及文件系统的带时间戳快照；分项返回采集错误 |
| `operations.create` | 提交类型化操作、目标 ID、期望配置哈希、幂等键和截止时间 |
| `operations.get` / `events` | 查询状态、阶段进度、脱敏日志和最终结果 |
| `operations.cancel` | 请求取消；已完成的不可逆步骤按该操作的恢复规则处理 |

写操作统一使用桌面 Job ID 作为幂等键。Agent 保存远端 operation journal，重复提交返回原结果；每个资源串行执行，修改前比较观测版本或配置哈希。结果明确区分“请求未送达”“已接受仍在运行”“成功”“失败并已恢复”“失败且需要人工处理”。日志不记录 Registry 密码、SSH 凭据、证书私钥或完整环境变量。

## 能力分批落地

| 阶段 | Agent 能力 | 验收重点 |
| --- | --- | --- |
| 1. 引导与只读 | 安装/升级/健康、服务器探测、CPU/内存/存储采集、容器/端口/Compose 清单、日志尾部 | 新旧服务器并存；断线重连；不改变现有服务 |
| 2. 发布 | 镜像拉取、容器或 Compose 部署、启停、版本切换、回滚 | 复用现有发布历史与 Job 语义；重复任务不重复发布 |
| 3. 入口 | Nginx 路由扫描、预览、备份、`nginx -t`、重载和失败恢复 | 现有配置哈希冲突时拒绝覆盖；不接管无关路由 |
| 4. 证书 | Certbot 环境预检、申请/续期、Nginx 容器证书可见性、续期钩子和访问验证 | 不抢占 80/443；验证 DNS/挑战路径；续期后正确重载 |

数据库浏览、任意文件传输和通用终端不属于首版 Agent。现有 CLI/MCP 仍调用桌面 Runtime，不绕过其确认和 Job 边界。

### 服务器资源采集

- **CPU：** 读取两次 `/proc/stat` 的累计计数计算区间使用率，同时返回逻辑核心数和 1/5/15 分钟负载。首次采样尚无区间数据时返回 `warming_up`，不显示虚假的 0%。
- **内存：** 从 `/proc/meminfo` 返回总量、`MemAvailable`、已用量及交换空间，单位统一为字节；界面明确“已用量 = 总量 − 可用量”，不把 Linux 缓存全部算成不可用内存。
- **存储：** 返回根文件系统及 Docker 数据目录所在文件系统的总量、可用量、使用率、挂载点和文件系统类型；两者在同一挂载点时只展示一次。排除 `tmpfs`、`proc` 等伪文件系统，避免把容器内文件系统当作宿主机磁盘。
- **采样与展示：** Agent 每约 10 秒更新内存和 CPU 快照；磁盘每约 60 秒更新。桌面服务器详情显示三张紧凑信息卡和“采集于”时间，断线或超时显示最后值及“数据已过期”，不把过期值当实时状态。首版不保存长期历史、不建立自动告警。
- **故障隔离：** CPU、内存、存储各自带 `status` 和错误信息；单项失败不妨碍其他指标和容器清单返回。数值采用整数/64 位字节，百分比由明确分母计算，防止单位和四舍五入不一致。

## 权限、安全与状态

- Agent API 只暴露允许列表中的类型化操作，不提供 `exec`、任意文件路径或未经限制的 Docker API 转发。路径限定在 iDeploy 管理目录及经预检批准的 Nginx/Certbot 文件。
- Docker socket 权限接近主机高权限；不能把加入 `docker` 组表述成低权限隔离。Docker、Nginx 和 Certbot 操作按能力分层，敏感操作使用固定参数与明确的目标校验。
- 配对凭据、Registry 密码和私钥不得进入 SQLite、Job payload、日志或测试样例。传输秘密时使用短生命周期通道；Agent 持久化仅保存必要的不可逆摘要或引用。
- Agent 与桌面端分别记录操作 ID、版本、资源、阶段和结果；桌面端为用户可见任务的权威记录，服务器实际状态为恢复和对账的依据。
- 新增服务器 Agent 元数据需要数据库迁移，已有服务器默认 `not_installed`，不因升级应用自动改动远端。

## 实施与验证顺序

先完成协议和安装包构建，再在开发机服务器做只读 Agent 垂直切片，包含 CPU/内存/存储采集。确认安装、升级回滚、认证、断线对账、资源指标口径和旧 SSH 模式均可靠后，逐项迁移发布操作；Nginx 与 Certbot 最后接入。每一项操作切换执行器前须有同等的失败恢复、幂等和回滚测试。最终在 macOS 运行 `go test -tags native ./...`、原生构建及应用打包，并在 Linux amd64/arm64 验证 Agent 二进制与 systemd 生命周期。

开发进度：已加入 Linux amd64/arm64 Agent 构建、首次安装和显式更新/卸载任务、Keychain 配对、SSH `-W` HTTP 转发，以及 CPU/内存/存储、容器/端口、日志、Nginx 的只读接口。容器启停、镜像拉取与标签、单容器替换/回滚、Compose 上传/拉取/启动、Nginx 应用、Certbot 申请/续期已使用类型化操作与远端幂等日志；旧版或未安装 Agent 的服务器在支持的操作上保留 SSH 路径。开发机服务器实测了安装、配对、资源、容器/端口和 Nginx 扫描；Nginx 写入恢复与容器替换恢复通过模拟故障测试。证书申请需要服务器预先配置 ACME Webroot 的 80 端口访问和完整的 `/etc/letsencrypt` Nginx 挂载；未满足时预检拒绝申请，不会停止现有代理。真实 Certbot 签发和 ARM64 systemd 生命周期尚未实测。
